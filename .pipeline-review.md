# GH-25 review: Save edits without approving + Reopen decided items

Reviewer: Kieran (TypeScript). Scope: `git diff origin/main...HEAD` in this worktree. `tsc --noEmit` clean for apps/console and packages/core. (Note: this file previously held a stale GH-10 review; replaced.)

## Correctness verdict: PASS

The SQL is careful and parameterized throughout; guards and jsonb operators are used correctly.

- `saveDraftEdits` (apps/console/src/lib/approvals.ts): the `CASE WHEN payload ? 'original_draft' THEN '{}'::jsonb ELSE ...` pattern correctly captures original_draft on the FIRST edit only, because all `payload` references on the RHS of `SET` evaluate against the pre-update row. `WHERE id = $1 AND status = 'pending_approval'` gives race safety against a concurrent decision, and the 0-row case throws instead of silently succeeding. `$2::text`/`$3::text` parameterization is right.
- The same first-edit CASE was correctly retrofitted into the `decideItem` edits branch, so Save edits followed by Save & approve does not clobber the true original. Good catch by the implementer.
- `decideItem` plain branch now folds `payload->>'draft_edited'` into `decision.edited` via `jsonb_set($2::jsonb, '{edited}', to_jsonb(coalesce(...::boolean, false)))` — correct SQL, NULL-safe via coalesce, and keeps the audit truthful when an operator saves edits and later plain-approves (or rejects).
- `reopenItem` (packages/core/src/db/items.ts): guarded `WHERE id = $1 AND status = 'resolved'`; `(payload - 'decision') || jsonb_build_object('decision_history', coalesce(payload->'decision_history','[]'::jsonb) || CASE WHEN payload ? 'decision' THEN jsonb_build_array(payload->'decision') ELSE '[]'::jsonb END)` is correct jsonb: array append via `||`, with `jsonb_build_array` wrapping the old decision so a jsonb string (legacy) or object appends as one element rather than being merged. All payload reads are old-row values, so no read-modify-write race.
- `isUniqueViolation` narrows `unknown` via a structural check on `code === "23505"` with no `any`. `ReopenConflictError` sets `name`, extends Error properly, and is exported from the barrel (packages/core/src/index.ts).
- RBAC: both new server actions call `requireDecider()` first (Clerk session check + `hasPermission(role, "approvals:decide")`), matching the existing GH-22 pattern. The Reopen control is additionally gated in the UI by `canDecide`.
- React/Next usage: `useActionState` with a `(prev, formData) => Promise<State>` action signature is correct React 19; `pending` as the third tuple element is right. The `formAction` closure on the Save edits button (`await saveEditsItemAction(formData); setEditing(false)`) mirrors the existing Save & approve button pattern.
- Copy: no em dashes; the conflict message is honest about the cause; CSS reuses existing GH-21 tokens (`--accent-tx`, `--tx3`, `--rej-tx`, `--font-ui`).

Findings:

- MAJOR (robustness): `isUniqueViolation` maps ANY 23505 raised by the reopen UPDATE to `ReopenConflictError`. Today the only unique constraint this UPDATE can trip is `items_dedupe_key_unresolved_idx` (migration 0004), so it works, but it is one future unique index away from lying to the user. Also check `err.constraint === "items_dedupe_key_unresolved_idx"` (node-postgres exposes `constraint` on DatabaseError). Cheap insurance. packages/core/src/db/items.ts.
- NIT: `ReopenButton` takes `id: string` and the caller does `String(item.id)`. If `Item["id"]` is already a string the wrapper is noise; if it is a number, type the prop from the source type instead of coercing at the call site. apps/console/src/app/approvals/page.tsx.
- NIT: `ReopenState` as `{ error: string | null }` is fine for now; consider a discriminated union if reopen ever returns success data.

## Efficacy verdict: PASS

Walking the runtime paths against the ticket goals:

1. Save edits leaves the item pending: yes. `saveDraftEdits` never touches `status`/`resolved_at` and records no `decision` key; only draft fields + `draft_edited: true` are merged. `revalidatePath("/approvals")` re-renders the server page, `toCardData` maps `payload.draft_edited === true` into `edited`, and the card shows a subtle "edited" note using the existing `approval-pane-timestamp` token. `original_draft` is captured exactly once (the CASE evaluates the pre-update payload).
2. Reopen preserves legacy string decisions: yes. `payload ? 'decision'` is a key-existence check (works for jsonb string or object values), and `jsonb_build_array` appends a bare string as a single history element. After reopen, `decision` is removed, so `DecidedRow`'s legacy branch cannot misfire on the next decide.
3. Dedupe conflict mapping works end to end: yes. The UPDATE flips status from `resolved` to `pending_approval`, which inserts into the partial index (`WHERE status <> 'resolved' AND payload->>'dedupe_key' IS NOT NULL`); a live twin raises 23505, node-postgres surfaces `code: "23505"`, `isUniqueViolation` catches it, `ReopenConflictError` propagates to the action.
4. The `instanceof ReopenConflictError` check is safe here: both the throw (packages/core) and the catch (the server action body) execute in the same Node process against the same imported class; no serialization boundary is crossed. Crucially, the action then RETURNS `{ error }` rather than throwing across the RSC boundary — thrown server-action errors get their messages redacted in production and would hit the error boundary instead of rendering inline. The design is correct.
5. `revalidatePath` inside a `useActionState` action works in Next 15: the action response carries the revalidated RSC payload, so both lists refresh in the same round trip as the state update. The reopened item moves lists without a manual refresh, and a successful retry returns `{ error: null }`, clearing a prior inline error.

Findings:

- MAJOR (edge case, non-blocking): two remaining crash paths are not friendly. (a) Save edits clicked after someone else decided the item: `saveDraftEdits` throws a plain `Error`, which propagates through the client `formAction` closure to the nearest error boundary with a redacted message in production. (b) Double-click / concurrent Reopen: the loser gets 0 rows, `reopenItem` throws a plain Error, and `reopenItemAction` rethrows — same redacted crash, despite the action having a perfectly good `ReopenState` channel to return "This item is no longer in that state, refresh and try again." The ticket only mandates friendly handling for the dedupe conflict, so not a blocker, but for a QA-fixes ticket these are the exact class of paper cut being fixed; both are one `return { error }` (or try/catch in the client closure) away. apps/console/src/app/approvals/actions.ts.
- NIT: after a successful reopen, `payload.draft_edited` survives, so the reopened card immediately shows "edited". That is truthful (the draft was edited) and I read it as correct, but call it out in the PR description so QA does not file it as a bug.

## Summary

PASS — correctness and efficacy both hold; two non-blocking MAJORs (constraint-name check on 23505; friendly returns for the stale-item race paths) recommended before or shortly after merge.

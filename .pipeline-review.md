## Nits

- `migrate.ts` `isMain` guard uses `import.meta.url === new URL(\`file://${process.argv[1]}\`).href`.
  This is fragile for paths containing spaces or special characters, because
  `import.meta.url` is percent-encoded while the hand-built `file://` string is
  not, so the comparison can produce a false negative. Prefer
  `pathToFileURL(process.argv[1]).href` from `node:url`. Works fine for the
  current worktree path; flagging for robustness.
- Migration runner wraps each file in `BEGIN`/`COMMIT`. That is correct today,
  but statements that cannot run inside a transaction (e.g.
  `CREATE INDEX CONCURRENTLY`) will fail when a future migration needs one.
  Not a problem for `0001_init.sql`; worth a comment or an escape hatch when the
  first such migration appears.
- `env.ts` is a hand-rolled `.env` parser. It is minimal, dev-scripts-only, and
  deliberately avoids adding a `dotenv` dependency, which is the right call. It
  does not handle multiline values or escaped quotes beyond a leading/trailing
  strip, which is acceptable for `DATABASE_URL`/`REDIS_URL`. No change required.
- `migrate`/`smoke` npm scripts run `npm run build` on every invocation. Fine,
  but it rebuilds the whole package each time. Acceptable for now.
- `smoke.ts` uses `redis.disconnect()` (abrupt) rather than `quit()`. Harmless
  for a one-shot smoke script.

## Correctness verdict

Strong. TypeScript is clean under the repo's strict config
(`strict`, `noUncheckedIndexedAccess`, NodeNext ESM) and builds with zero
errors, emitting the expected `dist/db/*.js` layout.

- ESM/NodeNext interop is correct: `import pg from "pg"; const { Pool } = pg;`
  (pg is CJS) and `import { Redis } from "ioredis"` both resolve and run.
- No `any`. `getPool().query<{ ok: number }>(...)` and
  `client.query<{ name: string }>(...)` are properly typed; `rows[0]?.ok`
  respects `noUncheckedIndexedAccess`.
- Migration runner is transactional (per-file `BEGIN`/`COMMIT` with `ROLLBACK`
  on error), idempotent (tracked in `schema_migrations`, `done` set skip), and
  concurrency-safe (session-level `pg_advisory_lock` acquired on a dedicated
  client and released in `finally`). Table creation happens after the lock, so
  concurrent first-runs cannot race.
- `MIGRATIONS_DIR` resolves from `dist/db` up to `packages/core/migrations`
  (SQL files intentionally not compiled) — correct.
- `loadEnv` resolves repo-root `.env` from `dist/env.js` and never overrides
  already-set env vars, so Railway's service env wins and the absent-`.env`
  case is a no-op — correct targeting for both environments.
- `requireEnv` treats empty string as missing — desirable.
- docker-compose: healthchecks on both services, named volumes for persistence,
  Redis AOF enabled, no obsolete `version` key. Good.

## Efficacy verdict

Verified at runtime, not just by reading:

- `docker compose up -d` brought both services to `healthy`.
- `npm run migrate -w @ai-manager/core` from the workspace root applied
  `0001_init.sql` against a clean volume (printed `Applied 0001_init.sql`) and
  was a no-op on re-run (`up to date, nothing to apply`); `schema_migrations`
  contained exactly one row. Idempotency and apply paths both confirmed.
- `npm run smoke -w @ai-manager/core` connected to both: `Postgres: ok`,
  `Redis: ok`.
- Railway path is sound by construction: scripts rely on `requireEnv` +
  `loadEnv` (which no-ops without a `.env`), so `DATABASE_URL=<url> npm run
  migrate -w @ai-manager/core` documented in `docs/railway.md` will work from a
  Railway-provisioned env. Deployed verification is correctly deferred to GH-10.
- Scope is necessary, sufficient, and correctly targeted: nothing beyond the
  ticket (no Railway CLI, no domain tables, backups explicitly deferred). No em
  dashes in user-facing copy; conventions match ARCHITECTURE.md.

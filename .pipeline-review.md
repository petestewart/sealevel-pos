## Efficacy verdict

PASS, with two watch items (majors below) that could surface during the manual deploy but have documented escape hatches.

- Env checklists vs code: worker table (DATABASE_URL, REDIS_URL, ANTHROPIC_API_KEY, NOVU_SECRET_KEY, NOVU_SUBSCRIBER_PETE/ALISON, WORKER_CONCURRENCY) matches actual usage in packages/core/src (redis.ts requires REDIS_URL, db/client.ts requires DATABASE_URL, queue/worker.ts reads WORKER_CONCURRENCY, notifications/emit.ts no-ops without NOVU_SECRET_KEY). Console table (DATABASE_URL, both Clerk keys) matches apps/console/src/lib/env.ts + middleware requirements; core's `requireEnv` is lazy, so the console not setting REDIS_URL is fine unless a console page later touches the queue.
- Worker healthcheck: works. Railway injects PORT, the worker binds it, healthcheckPath `/healthz` hits the express route that returns 200 unconditionally.
- loadEnv on Railway: correctly a no-op (no .env file, and it never overrides set vars).
- Migrations at predeploy: `npm run migrate -w @ai-manager/core` runs `npm run build && node dist/db/migrate.js`, i.e. it needs `tsc` (root devDependency) at predeploy time. Nixpacks' node provider installs devDependencies by default (NPM_CONFIG_PRODUCTION=false during build) and Railway's pre-deploy command runs in the built image, so this should work, but it is the most fragile link; see major finding 1.
- Following docs/railway.md top-to-bottom: sections 1-5 (existing) provision DBs, 6-7 create both services with config file paths, variables, domains, Clerk origin allowlisting, and the NEXT_PUBLIC build-time-inlining caveat. Section 9 gives concrete acceptance checks tied to GH-10 (healthchecks, heartbeat schedule, dead-letter via test-fail-demo, restart-survival). This is a followable runbook.

## Findings

Blockers: none.

Major:
1. docs/railway.md:78 (section 6, predeploy step) and apps/worker/railway.json:9 — the predeploy migration silently depends on devDependencies (typescript) being present in the deployed image, because `npm run migrate` re-runs `npm run build` (tsc). If Nixpacks/Railway ever prunes devDeps (someone sets NODE_ENV or NPM_CONFIG_PRODUCTION, or the builder changes), predeploy dies at `tsc`. Sturdier: build in buildCommand only and make preDeployCommand `node packages/core/dist/db/migrate.js` (no rebuild). At minimum add one runbook line naming this failure mode. Not a blocker: default Nixpacks behavior works today.
2. apps/worker/railway.json:3 and apps/console/railway.json:3 — no Node version pinning. Root package.json has `engines: { "node": ">=20" }`, which Nixpacks respects, but the open-ended range means the deployed Node major can jump on a rebuild. Pin (`"20.x"` engines or NIXPACKS_NODE_VERSION) or document why not. Given this ticket is about restart-survival and predictability, unplanned runtime major bumps are exactly the class of surprise to exclude.

Nit:
1. apps/worker/src/index.ts:109 — `Number(...)` of a malformed PORT yields NaN and `app.listen(NaN)` behavior is surprising. Pre-existing pattern (was already `Number(BULL_BOARD_PORT)`), fine to leave.
2. docs/railway.md:130-133 (section 8, step 4) — "if the default Nixpacks image lacks them" is known-true: the stock Nixpacks node image will not include postgresql-client 16+ or rclone. Acceptable since explicitly deferred to the Phase 0 checklist, but state it as a certainty.
3. docs/railway.md:100-104 (Bull Board exposure) — good catch documenting Bull Board's lack of auth; consider a follow-up ticket for basic auth on `/admin/queues` so the safe option is not purely procedural.

Conventions: no em dashes introduced (docs are internal, not user-facing copy in any case); doc style matches the existing runbook; no `any`; imports clean. Scope adhered to: no live-deploy claims, verification split into local evidence plus a deferred on-Railway repeat.

SUMMARY: PASS

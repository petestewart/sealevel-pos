# Review: GH-9 nightly pg_dump backup

Scope reviewed: scripts/backup/pg-backup.sh, docs/backups.md, .env.example additions, .gitignore line. (packages/core and docker-compose are prior merged work and out of scope.)

## Correctness

- `set -euo pipefail` present; script fails closed on any error.
- `DATABASE_URL` requiredness, `pg_dump`/`pg_restore` presence checks: correct.
- `BACKUP_RETENTION` validation: the `case ''|*[!0-9]*)` pattern correctly rejects empty/non-digit input, followed by a `>= 1` check. Sound.
- Quoting is correct throughout: `"$DATABASE_URL"`, `"$TMP_FILE"`, `"$BACKUP_DIR"/"$BACKUP_PREFIX"-*.dump`, `rm -f -- "$old"` (the `--` guards against filenames starting with `-`).
- `.partial` temp-file handling is correct: dump writes to `$DUMP_FILE.partial`, `pg_restore --list` verifies the archive is readable, then `mv` promotes it atomically only on success. On verification failure the partial is removed and the script exits via `fail`.
- Retention math: `ls -1t ... | tail -n +"$((BACKUP_RETENTION + 1))"` is the correct idiom to keep the newest N and list the rest for pruning (off-by-one correct: `tail -n +(N+1)` skips exactly the first N lines).
- `ls -1t` parsing: filenames are entirely script-controlled (`$BACKUP_PREFIX-$STAMP.dump`, timestamp format `%Y%m%dT%H%M%SZ`), so no spaces/newlines/globbing surprises in the names being parsed here. Acceptable given the controlled naming convention; would not be safe if `BACKUP_PREFIX` were attacker-influenced, but it's an env var the operator sets.
- Credential leakage: no `set -x`, and no log line ever echoes `$DATABASE_URL` or any derived secret. `pg_dump`/`pg_restore` invocations pass the URL as an argument (visible briefly in `ps` output, a real but low-severity concern common to all pg_dump usage and out of scope for this review) but nothing is written to stdout/log.
- rclone step: gated behind `BACKUP_RCLONE_REMOTE` being set, checks `rclone` is on PATH before use, fails loudly if missing. Straightforward `rclone copy`.

## Efficacy

- Railway delivery: docs describe a cron-service option (Option A) that works with only env changes (`DATABASE_URL` via Railway reference var, `BACKUP_RCLONE_REMOTE`, `RCLONE_CONFIG_*`), plus a documented future BullMQ option gated on GH-3. This satisfies "working locally now and on Railway with only env changes" — Option A requires creating a new Railway service, which is a platform configuration action rather than a code change; reasonable given the ticket's intent, but worth a passing note since it's slightly more than a pure env change. Not a blocker.
- Restore procedure: `pg_restore --no-owner`, explicit `createdb` before restore (never restores over the live DB by default), and a version-compatibility note (client tools must be >= server major version) are all present and correct.
- Restore drill: the documented drill (dump via the real script, `createdb`, `pg_restore` into a second DB, compare `schema_migrations` between source and restored copy, then `dropdb`) is a sound, concrete verification loop and directly proves the dump/restore path end to end.

## Nits

- If `pg_dump` fails partway through, `set -e` exits before any cleanup of `$TMP_FILE.partial` runs (the `rm -f "$TMP_FILE"` cleanup only fires on the `pg_restore --list` failure path, not on a `pg_dump` failure). Orphaned `.partial` files won't be caught by the retention prune loop (which globs `*.dump`, not `*.dump.partial`) and will accumulate silently in `BACKUP_DIR`. Not a correctness bug for backup integrity (a failed dump never gets promoted to a real `.dump`), but worth a one-line `trap` or comment for disk hygiene.
- `docs/backups.md` env var table matches the script's actual env vars and defaults exactly (`BACKUP_DIR=./backups`, `BACKUP_RETENTION=14`, `BACKUP_PREFIX=ai-manager`, `BACKUP_RCLONE_REMOTE` unset/local-only) — no discrepancies found between docs and script behavior.

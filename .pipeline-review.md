`noUncheckedIndexedAccess`) and exercising the no-op path at runtime

What holds up:

- `packages/core/src/notifications/emit.ts`: no `any`, proper union type
  for `ItemEventType`, injectable `TriggerFn` makes the module trivially
  testable without module mocking. Error containment is correct: the
  try/catch around `trigger(...)` guarantees emit never throws, matching
  the doc comment, and the smoke script proves it (step 3).
- The `trigger === defaultTrigger` guard is subtle but correct: with no
  key and the default trigger it short-circuits before any client is
  constructed; with an injected trigger it proceeds, which is exactly
  what the smoke tests need. `defaultTrigger` reads the env at call time
  (not module load), so late `loadEnv()` works.
- `configuredSubscriberIds()` degrades gracefully per missing var and
  returns `{ sent: false, reason: "no subscribers configured" }` when
  both are unset instead of triggering with an empty `to` array.
- Call site (`packages/core/src/tools/registry.ts`): minimal, gated on
  `status === "pending_approval"`, cannot fail item creation. Matches
  surrounding code style and import grouping.
- Migration `0003_notification_prefs.sql`: safe under the existing
  runner (per-file transaction, tracked in `schema_migrations`, advisory
  lock), so the non-idempotent seed INSERT and bare `CREATE TABLE`
  match the established convention (0002 does the same). Composite PK
  and the channel CHECK constraint are sensible.
- Exports in `packages/core/src/index.ts` follow the existing named
  export + `export type` pattern.

Minor notes (non-blocking):

1. Seed rows hardcode user_id `pete`/`alison` while the Novu subscriber
   ids are env-configurable (`NOVU_SUBSCRIBER_*`). If someone sets a
   non-default subscriber id, the table comment's claim "matches Novu
   subscriberId" silently becomes false. Fine for v1 with two known
   operators; revisit when the console starts reading this table.
2. Smoke step 4 fires a real trigger to the real subscribers when a key
   is present in `.env`, i.e. running the smoke can SMS Pete. The docs
   say so, but a louder warning log before sending would be kind.
3. `configuredSubscriberIds()` warns on every emit when a var is
   missing; acceptable at v1 volume.
4. `smoke.ts` mutates `process.env` and only partially restores it
   (subscriber defaults stay set). Fine for a process-scoped script.

## Efficacy: PASS with one setup-time risk to verify

The mechanism is sound. One trigger of one workflow to both subscribers,
with per-subscriber channel preferences deciding delivery, is exactly
how Novu models differential routing: the workflow has an SMS step and a
digest+email step; Pete's preferences enable only SMS (instant),
Alison's enable only email. Novu evaluates subscriber preferences per
channel step at delivery time, so a single `novu.trigger()` to
`[pete, alison]` yields an instant SMS to Pete and a digested email to
Alison. The digest step only affects the email branch, which only Alison
receives. Enforcement being dashboard-side with `notification_prefs` as
recorded intent is honestly documented in both the migration header and
docs/novu.md; nothing in the code pretends to enforce routing it does
not.

Risk to verify at setup time: the workflow trigger identifier
`item.pending_approval` contains a dot. The code uses the event type
verbatim as `workflowId`, and docs/novu.md step 4 instructs creating the
workflow with that exact identifier. Novu's dashboard auto-slugifies
workflow names to kebab-case, and depending on version the identifier
field may reject or rewrite dots. If it will not accept a dotted
identifier, triggers will fail to match any workflow and the feature
silently delivers nothing; because errors are contained by design,
failures surface only as log lines and `{ sent: false }`. Mitigation is
cheap: during the docs/novu.md setup, confirm the identifier saved
exactly as `item.pending_approval`; if the dashboard rejects it, add a
one-line event-type-to-workflowId mapping (e.g. dots to dashes) in
emit.ts. The smoke script's live step plus the Activity Feed check in
the docs will catch this on the first real run, so it is a documented
setup risk, not a code defect.

Also right: the with-key smoke path never claims Novu accepted the
workflow, only that the trigger call was made, and the docs direct the
user to the Activity Feed for end-to-end confirmation. Correct honesty
level for a system whose enforcement lives dashboard-side.

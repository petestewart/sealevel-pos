## Nits

1. `packages/core/src/tools/registry.ts` uses `BetaRunnableTool<any>` twice (the `toolsByName` record and `toolsForJob` return type) with no comment. The `any` is genuinely forced here — a heterogeneous tool registry needs an erased input type, and `unknown` will not satisfy the contravariant `run` parameter — but the project convention (never `any` without a justifying comment) still applies. Add a one-line comment explaining why.
2. `toolsByName` is a `Record<string, ...>` while the sibling registry (`jobs/registry.ts`) uses a `Map` (`jobById`). A `Map` would match the existing convention and make the `undefined` check in `toolsForJob` idiomatic rather than dependent on `noUncheckedIndexedAccess`. Not blocking; the current code is correct.
3. `packages/core/src/brain/smoke.ts` import ordering mixes levels: `./run.js` is imported before `../tools/registry.js`. Keep internal imports grouped consistently with sibling files.
4. `brain/smoke.ts` ends with `process.exit(0)` on success where `db/smoke.ts` closes its handles (`closePool`, `redis.disconnect`) and exits naturally. The hard exit is defensible (the pg pool may be open after a live `create_item` run), but a brief comment saying so would prevent a future cleanup regression; alternatively call `closePool()` and drop the forced exit.
5. `runJob` returns `Promise<string | null>`; the SDK's `stop_reason` is a string-literal union, so the return type could be tightened to the SDK type for free.

PASS.

- Compiles clean under strict; the one indexed access in `toolsForJob` is guarded, satisfying `noUncheckedIndexedAccess`.
- ESM: all relative imports carry `.js` extensions; SDK subpath imports (`@anthropic-ai/sdk/helpers/beta/zod`, `.../lib/tools/BetaRunnableTool`) resolve under NodeNext.
- SDK usage matches the verified surface: `client.beta.messages.toolRunner` awaited directly for the final message, `betaZodTool` shape (name/description/inputSchema/run returning string), `thinking: { type: "adaptive" }`, model values constrained by the new `BrainModel` union to the two locked models.
- `create_item` tool schema is a faithful subset of `CreateItemInput` (status enum correctly excludes `resolved`; `payload` as `z.record(z.string(), z.unknown())` matches `Record<string, unknown>`); it delegates to the existing `db/items.ts` helper rather than duplicating SQL.
- Lazy client construction means importing `@ai-manager/core` never requires `ANTHROPIC_API_KEY`; the smoke test's dry-run path relies on this and it holds.
- Deletions: none; `index.ts` changes are additive re-exports; `Job` gains only an optional `model` field, so existing job definitions (heartbeat) remain valid.

## Efficacy verdict

PASS, with one observation.

- Per-job tool scoping is real at runtime: `toolsForJob(job.tools)` maps declared names to registry entries and throws on unknown names, so the runner receives exactly the declared subset. There is no fallback to "all tools" and no shared mutable list. Empty `tools: []` yields an empty array, which the runner accepts (the heartbeat job proves this path).
- Per-job model selection is real: `job.model ?? DEFAULT_BRAIN_MODEL` reads the field at call time; `BrainModel` restricts values to `claude-opus-4-8` / `claude-sonnet-5` per the locked decisions.
- Observation (not a failure): no registered job currently sets `model` or uses `create_item`, so the sonnet path and the live tool-execution path are exercised only by the dry-run assertions in `brain/smoke.ts`. The first Phase 1 triage job will be the live proof; the acceptance criteria as written are met.
- The smoke test covers the right seams: unknown job id, exact subset resolution including order, unknown tool name, plus an optional live heartbeat run gated on `ANTHROPIC_API_KEY`.
